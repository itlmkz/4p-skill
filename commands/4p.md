Open the 4p advisory panel and, if a task was given, run it to completion.

The launcher is at `${CLAUDE_PLUGIN_ROOT}/panel/4p.py`. That path is already
resolved for you. Do not search for it.

## Step 1. Check the precondition

The panel lives in Herdr panes, so this session must run inside a Herdr pane.

```bash
test "${HERDR_ENV:-}" = 1 && echo inside-herdr || echo not-in-herdr
```

If it prints `not-in-herdr`, say that the panel needs a Herdr pane and stop. Do
not try to work around it.

## Step 2. Start the panel

Run the launcher. Pass the task through `4PP_TASK` so that quoting cannot break
it, and keep the task text verbatim. The name starts with a digit, so the shell
cannot assign it directly. Always set it with `env`:

```bash
env 4PP_TASK="$ARGUMENTS" python3 "${CLAUDE_PLUGIN_ROOT}/panel/4p.py"
```

Rules for this command:

- If `$ARGUMENTS` is empty, drop `env 4PP_TASK=...` entirely and start the panel
  standing by.
- If the task text contains a double quote, use single quotes around it, or a
  heredoc. Never let the shell expand or glob the task text.
- The panes run pi by default, because 4p is a pi tool and pi panes get their
  write tools removed at launch. Add `4PP_KIND=claude` (or another kind) after
  `env` to change that. Herdr must have that kind available.
- The launcher is idempotent. It reuses a live panel, repairs a drifted label,
  and fills in only what is missing. Never close and recreate a panel to reset it.
- If it fails, print the error it gave you and stop.

## Step 3. Report the panel

Print the panel table from the launcher output: role, pane, agent name, status.
Take the real agent names from that output. Names can carry a numeric suffix,
such as `tester-2`, when a base name is already live in another workspace. Never
assume a name.

If no task was given, stop here. The panel is standing by.

## Step 4. Collect the four reports

If a task was given, the launcher already fanned it out to all four panes. The
AMO got it marked `Full report (4p/report@1):`, so all four answer in the
report contract.

Do not start to implement before you collect and merge the reports. The panel
is the input to your work, not an afterthought.

Collect all four with one call. Give the Bash tool a timeout of 600000 ms,
because the collector waits up to 5 minutes per pane, in parallel:

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/panel/4p.py" --collect
```

It waits for every pane and takes one `4p/report@1` block from each. It
validates each block, checks the evidence of each finding, and prints one json
object:

```json
{
  "tab": "wJ:t3",
  "reports": {
    "contraire":  {"status": "ok", "source": "saved file", "report": {...}, "errors": [], "evidence_checks": [...]},
    "tester":     {"status": "ok", "source": "saved file", "report": {...}, "errors": [], "evidence_checks": [...]},
    "reviewer":   {"status": "ok", "source": "saved file", "report": {...}, "errors": [], "evidence_checks": [...]},
    "bigpicture": {"status": "ok", "source": "pane", "saved_file": "not saved", "report": {...}, "errors": [], "evidence_checks": [...]}
  },
  "all_ok": true
}
```

Read `status`, `report`, and `evidence_checks` for each role. Read `all_ok`
for the whole panel. The command exits 1 when `all_ok` is false. That is a
result, not a crash. Read the json anyway.

A role whose `status` is not `"ok"` failed. Report it as failed, with its status
and `errors`. Never guess what that pane meant, and never fill its seat yourself.

### Where each report comes from

`source` tells you where the collector found the report:

- `"saved file"`: the pane's self-check saved it to `/tmp/4pp/<tab>/<role>.json`.
  The self-check writes that file only when the report is valid. The collector
  uses it only when it is newer than the task. It must also be a regular file,
  owned by you, and under 1 MB.
- `"pane"`: the collector read the pane output instead. `saved_file` then says
  why it did not use the saved file.

A pi pane draws a full-screen UI, so its earlier output never reaches the
scrollback. A pane read then sees only the visible lines. So the saved file is
the reliable source.

A panel briefed before 0.5.0 does not know the save step. If its roles come back
with `source` `"pane"` and fail, re-send the briefs once with the task:

```bash
env 4PP_TASK="$ARGUMENTS" python3 "${CLAUDE_PLUGIN_ROOT}/panel/4p.py" --rebrief
```

Then run `--collect` again.

### The evidence checks

Every role result has `evidence_checks`. It is an empty list when the collector
found no report. Otherwise it has one entry for each finding, in finding order:

```json
{"index": 0, "finding": "r1", "kind": "file", "status": "ok", "file": "src/app.py", "line": 42,
 "in_diff": true, "excerpt": "   40 | ...\n   41 | ...\n>> 42 | ...\n   43 | ...\n   44 | ..."}
```

- `index` is the 0-based position of the finding in `report.findings`.
  `finding` is its id. Two findings can share an id, so match by `index`.
- `file` is repo-relative. It resolves against the git top level, or against
  the panel folder outside git. The collector never reads a path outside that root.
- `reason` is optional. It explains a status that is not `ok`.

| `status` | Meaning |
| --- | --- |
| `ok` | The file and the line exist. `excerpt` shows lines line-2 to line+2. |
| `file_missing` | The file does not exist, or it is a directory, a FIFO, or unreadable. An empty path also gets this status. |
| `outside_repo` | The path resolves outside the root. The collector did not read it. |
| `line_out_of_range` | The file has no such line, or `line` is missing or not an integer. |
| `not_checked` | The evidence kind is not `file`, or the cited file is over 8 MB. |

The excerpt shows each line as `   41 | text`. The cited line is `>> 42 | text`.
The line numbers are aligned to one width.

`in_diff` is true when the cited line is within 5 lines of a change in
`git diff HEAD`. Line numbers count in the current file. A deletion counts at
its place in the current file. An untracked file counts as changed. `in_diff`
is null when git cannot answer, or when the status is not `ok`. It is context,
not a verdict. A finding about unchanged code can be true.

### Check each finding before you act on it

This step is mandatory. Do it for each finding of each role, before the merge.

Apply this citation rule:

> A citation supports the claim only when the cited file exists and the cited line is within 5 lines of the code that supports the claim. Line numbers count in the current file.

Find the entry for each finding in `evidence_checks` by its `index`. Then:

1. Status `file_missing`, `outside_repo`, or `line_out_of_range`: the finding is
   unsupported. Say so with the `reason`, and do not act on it.
2. Status `ok`: compare the claim with the `excerpt` under the rule. If the
   excerpt does not support the claim, open the file at that line. Do this
   before you reject the finding. The excerpt shows 5 lines, but the rule
   allows 5 lines on each side.
3. Status `not_checked` with kind `file`: the file is over 8 MB. Open it at the
   cited line and apply the rule yourself.
4. Kind `command` or `output`: the collector does not check this evidence.
   Treat it as reported. Re-run the command yourself only for a blocking finding.
5. Any other kind, or a finding with no entry: treat it as reported. Confirm a
   blocking finding yourself before you act on it.

A finding with `blocks` true that you judge unsupported goes to the user as
"unsupported", with the reason. An unsupported non-blocking finding gets one
line in the merged view. Never drop a finding silently.

## Step 5. Merge and answer

Act only on findings that passed the check in Step 4.

Present one merged view, not four summaries:

1. Agreements first.
2. Then the single strongest objection per seat.
3. Then each blocking finding you judged unsupported, marked "unsupported",
   with the reason.
4. Then the unsupported non-blocking findings, one line each.
5. Then your own disposition.

In the merged view, mark each finding you act on as checked.

Use the fields that carry the decision: `verdict`, `confidence`,
`findings[].blocks`, `findings[].severity`, `assumptions`, `questions`, and
`could_not_verify`. A finding whose `blocks` is true is a real risk: data loss,
security, a broken deploy, an irreversible choice, or a silent behavior change.
Treat `confidence` below 0.6 as a signal to escalate, not to act.

Anything the panes flagged in `questions` belongs to the owner. Put those
decisions to the user with a recommendation. Never present a decision bare.

## Rapid checkpoint (AMO)

After the merge, the AMO seat is a decision checkpoint. Prompt it with each
decision and design choice as you work, one sentence per decision:

```bash
herdr agent prompt <contraire-name> "Decision: <one sentence>" --wait --timeout 60000
herdr agent read <contraire-name> --source recent-unwrapped --lines 40
```

Take `<contraire-name>` from the launcher output. Checkpoint before an
architecture choice, before more than 20 lines of a new approach, and before
you touch auth, data, payments, or anything irreversible.

The answer is three lines, not json:

```
verdict: yes|yes_but|no_but|no_critical
reason: <one sentence>
watch: <optional watch items>
```

| Verdict | What you do |
| --- | --- |
| `yes` | Proceed. |
| `yes_but` | Proceed. Tell the user the watch item at the end. |
| `no_but` | Apply the fix in `reason` first, then proceed. |
| `no_critical` | Stop all work. Give the user the reason and a recommendation, and wait for the decision. |

Never override a `no_critical`. Do not ask the AMO for a full report on a single
decision. The full report is for the initial task review only.

## Writing rules

The panes advise. You are the only writer. Apply any patch yourself.

Everything the user reads follows these rules:

- English, in Simplified Technical English. One sentence, 20 words maximum.
  Active voice.
- No em dashes.
- Verdict first, then the evidence. Every claim carries a file:line, a command,
  or observed output.
- Do not quote pane json verbatim. Rewrite it.
- Separate blocking findings from nits. Say plainly when something is fine.

## If a pane cannot write

Panel panes are advisors. They are briefed not to change repo files or git state.
If a pane proposes a patch, apply it yourself.
